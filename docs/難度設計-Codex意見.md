# 台北政壇大富翁｜CPU 難度設計
- 首頁新增「輕鬆／普通／困難」，預設普通。三檔每人開局都是 $2,000、1,000 位支持者。
- 輕鬆仍會買地、拉攏里長，但出手較保守。普通延續現有玩法。困難更會留現金、搶整區、把握選前衝刺。
- 建議只調 CPU 的選擇。同樣的骰子、牌堆、戰將技能和獎懲，讓玩家看得出電腦贏在哪一步。

## 現在的 CPU 怎麼玩

| 決策 | 已經做得好的地方 | 容易吃虧的地方 |
| --- | --- | --- |
| 選骰、搭捷運（`cpuDiceCount`、`cpuRollValue`） | 算一顆的 6 種結果和兩顆的 36 種組合，知道兩顆骰的 7 點比 2 點常見。會避開高過路費、倒戈多的格子。同分用兩顆。搭捷運前也會平均估算下車後兩種方向，分數比原地高逾 10 才搭。 | 主要看落點，漏算沿途經過起點的 $400 和經過自家地標時的加蓋機會。空地和無主里長都以「全價再加 $200」估值，里長實際按次付半價，第二次拜訪就可能拿下。到對手里長格也只算損失，漏掉有勝算的拔樁機會。 |
| 買地、拜訪、加蓋（`offerBuy`、`offerChief`、`offerUpgrade`、`offerPassBuild`） | 買地或拜訪後保留 $200，加蓋後保留 $400。遇到免費加蓋會先選接近完工的，階段相同就挑較貴的。 | 保留金固定，附近有昂貴敵地時也一樣。首次拜訪和第二次拿下里長的門檻相同，湊齊整區每回合多 100 位支持者也沒列入判斷。 |
| 擲骰前（`cpuPreRoll`、`preRoll`） | 順序是辯論、拉攏里長、神秘金援、企業贊助、造勢、遠端任務。拉攏會留 $300，偏向便宜的目標，拜訪過通常更便宜也更快。金援在缺錢時才考慮，並派人脈最高的戰將。有完工地標且現金少於 $400 才接企業贊助，下半場且現金至少 $700 才造勢。 | 上層先選動作，外層才檢查它是否做過。若它仍排第一，CPU 會直接擲骰，漏掉其他可做的行動。下半場一有錢就可能花掉兩次造勢機會，錯過最後一回合 ×2。拉攏、金援也沒先確認戰將能否趕在投票前回來。 |
| 戰將配置（`onRecruit`、`onOwnChief`、`cpuBestMission`、`remoteMission`） | 招募偏好有自家里長的出身區，會找低忠誠的對手戰將挖角。任務會比較戰將、地點、遠端折扣和每回合平均收入，缺錢時提高募款權重。遠端派遣有兩人以上時會留一位待命。 | 挖角挑第一位合格者。駐守有 60% 機率選第一位待命戰將，遠端也固定把第一位排除在候選之外。可能留錯人、派出來不及結算的任務，或在樁腳已加滿時仍替選民服務加分。 |
| 拔樁、辯論（`onRivalChief`、`cpuWantsDebate`、`debate`、`duel`） | 把能力、剋招、守方偏好和骰子組合算進三戰兩勝的估計，挑勝算最高的戰將。拔樁門檻是落後時 40%、其餘 50%。辯論須在下半場且落後第一名至少 600 位支持者，估計勝算達 50% 才出手。 | 門檻用「每輪都出最佳招」算，實戰只有 70% 走最佳招分支，其餘從三招等機率抽，估計有時偏高。拔樁也沒分搶下能湊整區的里長，或只剩一輪收入的里長。辯論事前與開打各算一次，對手沒待命戰將時，候選人的偏好可能重抽。 |
| 英文挑戰（`quiz.js`） | CPU 固定 60% 答對，遊戲本身可關閉英文挑戰。 | 英文答對率適合維持固定，玩家可用首頁既有的「測驗程度」選題。 |

## 三檔的首版設定

以下門檻是試玩起點。保留金指付完費用後手上至少要剩的現金。每檔仍須符合原本的行動資格與費用。

| 決策 | 輕鬆 | 普通（預設） | 困難 |
| --- | --- | --- | --- |
| 擲幾顆 | 固定兩顆，保留移動速度和正常收益。捷運也以兩顆的落點分數比較。 | 用目前落點期望分，同分兩顆。 | 沿每個可能點數計入起點獎金、可負擔的沿路加蓋，以及下列買地與拜訪判斷；依實際分布加權。捷運用同一套評分。 |
| 買地／拜訪／付費加蓋 | 分別保留 $300／$300／$500，現金充足照買。 | $200／$200／$400。 | 用動態保留金 B。買地、最後一次拜訪、加蓋都留 B，第一次拜訪留 B + $100。能立刻湊整區或把地標蓋到完工可少留 $100，最低仍留 $200。最後兩回合只在下一次擲骰前能派戰將，且戰將可在投票日前完成拉攏時，才做首次拜訪。 |
| 拉攏里長與派任務 | 只拉攏已拜訪的里長，留 $400。遠端派任務至少有兩位待命時才派，選現有評分最高的可行任務。 | 拉攏留 $300，挑最便宜的目標。遠端沿用兩位以上留一位、只有一位時 50% 考慮派遣。 | 拉攏留 B，優先能及時補齊整區且較快完成的目標，同等時選便宜的。用任務結算日的支持者倍率和手頭現金比較收益；付費任務須留 B，選民服務只在仍能加固樁腳時給 +15 分。 |
| 拔樁（估計整場勝率） | 65%，每輪 50% 走最佳招分支，其餘均勻抽招。 | 沿用畫面所示的最佳招估計，落後 40%、其餘 50%。實戰維持 70% 走最佳招分支。 | 估計與實際都用每輪最佳招。基本 55%，攻下能湊齊整區且還有至少 3 次自己的回合開始，降到 45%。 |
| 辯論（估計整場勝率） | 75%，且付 $100 後至少留 $300。 | 50%，照目前資格。 | 一般至少 60%，付完須留 B。若最後三回合落後、攻守差距在一場勝利可追回的範圍，降到 45%。 |
| 金援、贊助、造勢 | 不主動找神秘金援。贊助沿用現有條件。造勢維持下半場有 $700 才辦，全場最多一場。 | 沿用現有門檻，造勢最多兩場。 | 金援只在現金低於 B、無合適的及時募款任務，且最高成功率至少 75% 或具免醜聞技能時考慮。贊助只在現金低於 B 且預估有下一輪大額支出時接。造勢留到最後一輪，付完仍須留 B；同回合有餘裕可辦兩場。 |

- **動態保留金 B**取 $200 和「下次回合開始預計應付的地方經營費與地標維護費，加上前方 12 格最貴的一筆敵方過路費」兩者較高，總額上限 $800。骰子路徑估分時把經過起點的獎金列入可花現金，再按經過順序扣除預計加蓋費，用剩餘現金判斷落點的購買力。困難檔估分初值可用 $1 折 0.5 分（現金低於 B 時折 1 分），一位支持者折 1 分，投票日前至少還有兩次自己的回合開始時，將新增的每回合支持收入先計兩次，否則只計實際剩餘次數。可完成整區時把每回合 +100 一併計入。
- **任務何時算來得及**用「目前回合 + 所需回合 ≤ 投票日」判斷，因為戰將在自己的回合開始結算。三檔共用這個基本檢查。困難檔有兩位以上可派時，前方 12 格有敵方里長就保留對其中任一格勝算最高的戰將；只有一位時，若前方有達拔樁門檻的目標就留人，其餘情況可以派任務。
- **辯論可追回的差距**按當回合的選前衝刺倍率與倒戈上限估算，因為倒戈使一方加、另一方減；正常勝利最多縮小 `2 × round(250 × 倍率)`。輕鬆和困難的勝率估計要和實際出招一致。輕鬆先用 `0.5 × 最佳招單輪勝率 + 0.5 × 三招單輪勝率平均` 算單輪，再轉三戰兩勝。

## 推薦做法與程式接線

同一起跑點比較容易看出策略差異。若改成困難每位 CPU 開局 $2,500，對上三位時桌上就會額外多 $1,500，先買地和拉攏里長的機會會一起增加，且每回合都能累積支持者。輕鬆讓真人多 300 位支持者雖容易說明，卻較少改變前期能做的事。首版只調決策，結算仍按存活玩家的支持者排名，剩一人則提前結束。

| 檔案 | 建議修改 |
| --- | --- |
| `src/data.js`、`src/title.js` | 在 `data.js` 集中放三檔策略設定。首頁 `TitleScene.init` 將 `opts.difficulty` 預設為 `normal`，讀舊設定後驗證 `easy / normal / hard`。用 `optionRow` 加一排「難度」，橫版放右欄第三排，直版加第六排並調整開始按鈕位置，確認兩版都不重疊。「朋友輪流玩」時停用這排。沿用現有 `options` 儲存與 `scene.start('game', { ...this.opts })`。 |
| `src/game.js` 的選骰與花費 | `GameScene.init(data)` 驗證並把難度存成局內 `this.difficulty`，缺值回普通。`playTurn` 將它傳給 `cpuDiceCount(p, difficulty)`，再往下傳給 `cpuRollValue(p, pos, dir, difficulty)` 與 `cpuTileValue(p, i, difficulty)`。捷運分支也傳同一檔。讓 `offerBuy`、`offerChief`、`offerUpgrade`、`offerPassBuild` 共用 `cpuCanSpend(p, cost, kind, i, difficulty)`，讓落點評分和真的付款時使用同一套門檻。 |
| `src/game.js` 的擲骰前行動 | 改成 `cpuPreRoll(p, difficulty, eligible)`，由 `preRoll` 先依合法動作和本回合紀錄過濾，再挑最高順位。普通保留現有優先序，輕鬆依表限縮選項，困難在最後一輪優先評估造勢與辯論。困難只讓尚有剩餘次數且仍付得起的造勢進入第二次候選，其餘動作每種每回合最多一次。 |
| `src/generals.js` | 將 `difficulty` 傳給 `cpuWoo`、`woo`、`cpuWantsDark`、`dark`、`cpuWantsRemote`、`remoteMission`、`onOwnChief`、`cpuBestMission`、`onRivalChief`、`cpuWantsDebate` 和 `debate` 的 CPU 分支。拉攏、任務及辯論各共用候選計算，預選後把同一個方案交給執行端；辯論連守方偏好一併傳入，避免重抽。`stakeBattle` 和 `debate` 把 CPU 的出招策略傳給 `duel`，沿用 `roundWinProb` 與三戰兩勝公式，真人選招照舊。拉攏若改派另一位人選，對話框的按鈕值和預選要用同一組目標與戰將。 |
| 驗收 | 先核對真人付款、骰子、牌堆、戰將獎懲和英文答對率沿用原規則，再測兩種版面、舊設定、輪流玩、回合邊界、造勢次數與現金門檻。用固定種子的多場對局比較各檔，分開看 1、2、3 位 CPU 和 30、50、80 回合；至少記真人勝率、落後第一名的差距和破產率。若三檔差距不穩，先調保留金與選前行動門檻。 |

本報告根據程式碼靜態閱讀。各檔門檻尚未經過對局驗證。
